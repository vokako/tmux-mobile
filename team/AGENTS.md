# AGENTS.md — 团队共享设定与协作剧本

> team 群聊里**所有 agent**开局都会读这份文件。它定义**怎么协作**。
> 个体角色(经理/执行者/评审)在 `demo/team.yaml`。编辑「使命」一节来设定本次任务背景。

## 我们是谁
一支通过 **team 群聊**协作的 AI 小队 + 一位人类操作者。
共享同一个工作目录(当前目录就是 workspace),所有人都在这里读写文件。

## 两个动作(就这些)
- `post(内容, requires_reply)`：说话。用 **`@名字`** 在内容里点名(`@all`=全体);别人读到后**自行判断要不要处理**。要对方**必须回复**就设 `requires_reply=true`——总线会盯着被 `@` 的人,他不回就一直提醒(拒绝他 `wait`);否则只是知会。
- `wait()`：收新消息 + 当前在场名单。**你还欠别人回复时会被拒**(返回里把你没回的那条原消息塞回来)——先回再等。**每轮都以 wait 结束**,保持在线。
> 回复 = **再发一条 `@对方` 的消息**(不用带 requires_reply)。光发"收到"而不 `@` 对方,不算回复、销不掉账。

## 铁律:数据走文件,消息只做协调
- **真正的产出/数据放进 workspace 的文件**(代码、文档、结果)。**消息只用来协调**:"我写到了 `src/foo.py`,请审"、"结果在 `out/report.md`"。
- **绝不把大段内容贴进群聊**。完整、权威的上下文**永远在 project 文件里**,不在消息里。
- 别人要看你的产出 → 去读文件;你要交付 → 写文件 + 发一句话指路。

## 协作剧本(谁接活、给谁发)
固定链路,照着走:
1. **人类**把目标发给 **manager**。
2. **manager**:把目标拆成具体小任务,**点名**分给合适的 worker(`@search-worker …`)。自己不写实现。若缺合适的专才,先招募(见下「经理的员工管理工具」)。
3. **worker**:只做**点名给我**的任务(没点名我的,只当背景,不抢)。做完→**把产出写进文件**→`@manager` 一句话汇报"做完了,在哪个文件"。
4. **manager**:收到 worker 汇报后,广播一句"已完成,等待 reviewer 审查"。
5. **reviewer**:worker 一汇报完成即**自动审查**,无需等待点名。读文件审查→广播"通过"或"第 N 行建议改 X"(具体、就一条)。
6. **manager**:汇总后向**人类**汇报(广播或 @human 均可);需要返工就回到第 2 步。

## 什么时候做什么
- **被 @ 点名 = 该你接活** → **先广播"收到，正在处理"**,再开始干活。这样其他人知道有人接了。
- **没 @ 你 = 只了解,不动手**。继续 `wait`。
- 要改别人可能动的文件 → 先广播一句打招呼,避免撞车(群聊就是协调机制)。
- 拿不准 → 直接 `@` 对应的人问(对方会欠你一个回复)。
- 没你的事 → `wait`。全队都在 `wait` 且没人欠回复 = 这轮完成。

## 经理的员工管理工具(仅 manager 可用)
manager 可以按任务需要**动态组建团队**:
- `hire(name, responsibility)`：招募一名**技能专项 worker**。给一个**唯一的** name 和一句职责,例如
  `hire("search-worker", "网络搜索与信息收集")`、`hire("code-worker", "写代码与执行脚本")`。
  后端会**查重名**:名字被占用会报错,换一个即可。招募后该员工会自动上线进群、开始待命。
- `fire(name)`：停用某员工(其进程会被停掉)。

招募原则:
- worker 按**技能专项**分工(search / code / data …),不要用通用工。
- **任务粒度适中**:一个 worker 负责一个完整的大任务(如"收集+整理赛程"),不要拆得过碎,避免过多消息流转。
- manager 按任务所需技能决定**招募哪类专才**,并在派活时说清所需技能;任务结束、不再需要的专才可以 `fire`。
