**Delivery correctness (the bug tails the gate found).**
- #248 — the server's mention parser split on `@` without a word boundary,
  so `a@bob` delivered to bob. One shared address rule in code points on
  both client and server, one pinned table.
- #249 — the big one: 21 commits rebuilding turn-fact persistence. Two
  pending queues (memory + deliveries table) disagreed, the in-memory one
  silently evicted past 16, restart rehydration came back in HashMap order,
  and a prompt+stop inside one second read as idle. Now every turn fact goes
  through one serialized entry ordered by one process counter under the
  ORDER lock (the persisted activity row id orders only the REPLAY after a
  restart), receipts key on the delivery row, and a restart rebuilds an
  open turn from the log.
- #250 — a message typed within ~1 s of two others never arrived. The loss
  itself is established (the message was posted and its delivery recorded;
  no hook, no kiro history); what was never proven is its CAUSE — no other
  paste ran that second, and the pane being in copy-mode stayed the
  strongest candidate. A separate bug the investigation did prove at source
  level — the shared named tmux paste buffer racing across panes — was
  fixed on its own evidence: every paste now gets its own buffer, and a
  pane in copy-mode refuses a send with an immediate warn instead of
  swallowing the line. #251 — the real-tmux tests
  for this learned to clean up after themselves even when they fail (leaked
  sessions had been auto-adopted as projects).

## The stall (2026-09-27 12:18 → 09-28 02:30 UTC)

Source: `temp/stall-analysis.md` (read-only state.db audit; "delivered" =
what the recipient's pane actually received, never what the sender
believed). The durable content is folded in here; the temp file is scratch.

Six routing failures in 14 hours. Five were the same shape: **the merge
verdict never reached the one agent allowed to merge.** The worst two —
3 h 27 min (#248's final SHIP) and 46 min (#241's version SHIP) — both ended
only when the owner asked "现在进度怎么样" / "好像又停掉了". The sixth was an
assignee idle with its issue in `doing`, noticed 11 minutes later by a
teammate manually running `tmm agent list`.

Root causes, by count (an event can have several):
- **(a) the final reply went to whoever opened the turn, not to whoever
  needed to decide — 5 events.** Worse than documented: `start_turn`
  REPLACED the reply edge on every new input, so a `[reply]` landing
  mid-turn erased the real requester. 27 of 404 turns in the window lost
  their requester this way.
- **(c) the conclusion was written as a board note that notified nobody who
  needed it — 4 events.** The code notified only the assignee; an assignee
  noting its own issue reached no one, and the reporter never heard
  anything — while board.md already documented the opposite and a unit test
  pinned the wrong behavior.
- **(e) other — 3 events:** an edge overwritten mid-turn, a self-filed issue
  with no second party to receive the handoff, the idle-assignee case.

The amplifier was queue latency. builder (kiro, queue mode) received 238
prompts in the window with a median delivery delay of ~19.5 min (p90 ≈ 44,
max 106; 178 over 10 min) while the other two agents sat at a ~15 s median.
Acting on stale information caused visible rework: three review handoffs
rejected because 26–48-minute-old corrections hadn't arrived; a done issue
moved back to review from a 29-minute-old message. And because nobody
trusted a note to arrive, 60 of 78 board-reply messages were a note AND an
@-send of the same text — doubling the very queue that caused the distrust.

The sentence to keep: **every time the merger heard nothing, builder
believed it had notified the orchestrator** — its notes and final replies
all said "ready for orchestrator to merge". An agent's own words are not
routing. (This is tenet 8 — derive, never self-report — applied to the
collaboration loop itself.) When validator wrote "SHIP/blocker always also
@orchestrator" into its own memory at 01:09, its deliveries turned reliable
immediately — proof the rule works and proof of its limits: it lived in one
agent's memory, not in the frame.

## The mechanism improvements

The stall analysis proposed M1/M2 (/M3) and explicitly rejected four
alternatives. What actually landed:

- **M1 → #255** (`0634453c`): a board note is delivered to the issue's
  reporter AND assignee, minus the author and minus human — recipients
  derived from the issue's declared parties, never parsed from the note's
  text. This made docs, code and test agree for the first time, and the
  tmm-cli skill now says "a note reaches both sides; don't also @ them" —
  removing the need for the double-send that produced ~60 duplicate
  deliveries per 14 h. Would have cut both owner-chasing stalls to ≈ 0.
- **M2 → #256** (`66efd264` and follow-ups): a turn's reply edge
  ACCUMULATES distinct requesters until the turn ends instead of being
  replaced per input; restart recovery rebuilds the edge from all inputs
  since the last turn end. `[reply]` still never creates a reverse edge
  (non-negotiable 11 unchanged). A true bug fix, not a feature: 6.7 % of
  turns were affected.
- **#257 — server-side coalescing** (`4db29c28`…`6d536ed0`): the analysis
  had REJECTED this as out of scope ("要改投递模型…改动面大"). It was then
  adopted deliberately when the queue-latency numbers proved it was the real
  pain, and built to the tenets: only a busy queue-mode kiro/codex holds
  lines; held lines live in the database (survive restart), flush as ONE
  prompt at turn end with every requester recorded, degrade to plain typing
  at the next trigger past 300 s — NO background timer (validator's
  correction to the owner-facing wording stands: the 300 s is a threshold
  checked at the next trigger, not a guarantee). The review caught one more
  real defect before merge: the requesters column was written in a second
  UPDATE after the row's INSERT, so a restart in between — or a swallowed
  UPDATE failure — could have left a truncated prompt with nobody to reply
  to (caught in review, never observed live). Fixed to one atomic INSERT
  inside the ORDER lock, with a fault-injection regression (a failing
  INSERT leaves no half-written row). Verified live: six messages to a busy
  kiro became one prompt, one reply each to both senders.
- **#258 — group actions** grew from the same "a team is one object" theme:
  the verbs that existed per card now exist on All and on team names.

**M3 — derive "who should move next" (issue in `doing` with an idle
assignee; `review` with a note newer than the reporter's last turn) as a
DISPLAYED signal, never an auto-nudge — remains open and unimplemented.**
It is the only proposal without an issue; file it when the next stall says
the two shipped mechanisms left a gap.

Rejected candidates (keep rejecting): a `tmm board ship/fix` verdict command
(a second mechanism for what a note now does); routing replies to an issue's
reporter by parsing `#N` from message bodies (deriving from an agent's
words); prompt/team-rule-only fixes (worked for exactly one agent's
memory).

## Decisions worth keeping

Where each lives so it survives this document:

1. **A note reaches both parties of an issue; don't also @ them over the
   same content.** The standing exception, kept deliberately after #255:
   verdicts (SHIP / blocker) still direct-@ the merge owner. — board.md +
   `tmm-cli` skill (#255).
2. **A turn's reply goes to everyone who put input into it; `[reply]` builds
   no reverse edge.** — agent-status.md, AGENTS.md non-negotiable 11 (#256).
3. **Busy queue-mode agents get coalesced, DB-persisted delivery; the 300 s
   mark is a threshold at the next trigger, not a timer.** — hub-composer.md
   (#257).
4. **An agent's own words are not routing, and not status.** Edges and state
   are derived from observed facts; a pane never vouches for itself. —
   tenet 8, now with the stall as its incident record.
5. **Input mode is offered only where a door was measured working (kiro,
   codex), default queue there; codex's door is its existing `-c`
   overrides, and a backend without a measured door keeps its CLI's
   behaviour.** — agents-overview.md (#245/#254).
6. **One address rule for client and server — two implementations mirrored
   by one pinned case table, never two rules.** — hub-composer.md (#248).
7. **The release ritual that worked:** the bump lands only after the gate's
   blockers and added scope pass; review is near-blind (issue + room for
   context, but only the diff, personally re-run gates, and the project's
   own rules decide); the worktree freezes at the review HEAD; the tag waits
   for the owner. The blockers the gate caught — four in the range audit
   alone, later an in-word-@ misdelivery and a two-step requesters write,
   among others — are the evidence it earns its cost. —
   guidance/process.md §5.
