# Agent Status — derived state, telemetry, deliveries and recovery

How the four derived states (`running | waiting | idle | failed`) come out of hook facts, what the activity log keeps, how a typed line is proven delivered, the four invariants of hook-sourced auto-replies, the pane-sniffed vitals, and the auto-`continue` recovery for transient model errors. Companion to `agents-overview.md` and `agent-lifecycle.md`.

## Rules and their reasons

Each entry is a decision with the reason it was made; treat them as normative. They lived in the root `CLAUDE.md` until 2026-09-02 (board #73), when that file became an index and the rules moved next to the design they belong to.

### Status is the turn bracket, and pane activity is NOT work

the hooks report all four edges of a turn (`userPromptSubmit` opens, tools run inside, an ask suspends, `stop`/`tmm done` closes), so `derive_from` is just "which boundary is newest" → exactly four states `running | waiting | idle | failed`, with `since` = the turn's START so a client can render "running 2m14s". `tmm status working|blocked` maps onto `running|waiting` (the CLI's vocabulary is wider than the UI's). The rule that had to go: `window_activity` newer than the last stop used to mean `working`, but an agent TUI repaints after answering (spinner, status line, cursor), so every finished agent read `working` forever. Pane activity now only speaks for a window that has produced NO hook facts at all (a hookless backend, a hand-started window). `Rec` keeps turn ends (`end`) and asks (`ask`) in separate fields for the same reason — one Option cannot answer "is a turn running" once a permission prompt overwrites a stop.

**Claude's `idle_prompt` is NOT an ask** (board #75, measured 2026-09-02: all 7 `input_required` rows in state.db sat exactly 60 s after `completed`): it is Claude Code's idle reminder fired AFTER the turn ended, and read as `input_required` it flipped every finished Claude agent to amber `waiting for you` a minute later. `consume_file` drops it before `normalize` (silently — already-spawned agents still emit it), and no matcher subscribes to it; `agent_needs_input` (a real question) stays `input_required`.

**How the four states RENDER on the card** (review, 2026-09-03): the dot speaks `stateDotColor` — accent in motion, `--status-warn` waiting/blocked, `--status-danger` failed, achromatic `--status-sleep` at rest — and `running` alone adds the `.live-dot` halo + breathe (`stateIsLive`, design-language.md). That left `waiting` — the one state that needs the HUMAN — as a 6px static amber dot beside a breathing neighbour, the weakest signal on the card. So the CARD carries it now: `stateNeedsYou(state)` (pure, pinned against `stateDotColor`'s amber states, and never true together with `stateIsLive`) puts `.acard.needs` on the card — the same `--status-warn` token as a 1px border + 1px inset ring (inset because the strip clips outward shadows) and a 9% wash — plus the word `needs you` (`blocked` keeps its own word) at `--fs-micro` beside the dot. Deliberately STATIC: the breathe means "a turn is open", and a suspended turn is not one; no new colour, no new mechanism — one token, worn by the card instead of only by the dot. Selection keeps its accent frame on top; the wash, the word and the dot still say waiting. `Hub.source.test.ts` pins the class, the gate and the token.

### A `tmm status` NOTE is the work made visible, and the state word is not

hooks bracket a turn but never say what it is FOR, so the note is the payload and the declared state is secondary — the agent's name plus its sentence, at EVERY feed level (like receipts), never a tool-lane boundary (it was written mid-run; closing the lane there would fragment it), and a note-less claim is DROPPED because derived `running`/`idle` beats a typed word. `waiting`/`blocked` notes take the attention colour. The other half is the prompt: `build_prompt` leads with `tmm status working "<what you are doing right now>"` + when to send one, and casts `tmm send` as the INTERRUPTING channel for something that needs a person — progress is ambient, messages are addressed. Owner symptom that drove it: "经常一直在做但是没有同步状态" (2026-08-19). An already-spawned agent keeps its old prompt (see `docs/unresolved.md`).

### The activity log is DURABLE, and a status note is a MESSAGE

tool calls, prompts, receipts and notes lived in a 120-entry in-memory ring, so a restart erased every tool lane while the messages around them survived — a feed with holes in it (owner, 2026-08-19: "重启就没了"). `activity` (state.db v9) is now the record: `push` inserts fail-soft (telemetry may never block what it observes), `recent_events` reads the DB (tail-first, `LOAD_EVENTS`) and falls back to the ring when there is no database, and a prune every 256 inserts keeps `KEEP_EVENTS` per session. Under `cfg(test)` both halves are off so `cargo test` cannot write invented sessions into the real state.db; the SQL is tested directly in `store.rs`. A `tmm status` note is no longer an event at all — `hub_status` POSTS it as `[tmm status <state>] <note>` from the AGENT (record-only, so an `@name` in a note can never type into a peer), because the owner asked for it in message form and because the room is what persists. A note-less claim posts nothing.

**A `tmm done` SUMMARY is the same case and was worse**: `[tmm] done — …` folded into a grey sys row that the chat level DROPS, so the agent's own account of what it finished vanished where a reader looks (owner again, 2026-08-19: "返回的状态信息要用消息的形式展示在对话里") — it is now `[tmm done] <summary>` from the agent, while a summary-less done stays a lifecycle line because nothing was said. `statusNote()` (pure + tested) reads both markers and strips them client-side — the bubble is exactly the bubble any other message gets (owner, 2026-08-19: "status 消息的样式要和普通消息一样就行"; a dimmer bubble with an attention border was the same mistake in a new costume, since a second visual species is what made these read as telemetry), with ONE header adornment added on request (owner, 2026-08-20): the bubble head carries a state BADGE (dot + state word in the .pg-tag pill dialect), coloured by `noteStateColor()` in the ONE progressive status language (same day: accent=in motion, ok-green=ended well, warn=needs a person, danger=failed, grey=unknown/at rest — `stateDotColor` speaks it too, and a test pins the two readers together; a spinner is never green, which is why working stopped being --status-ok) — NOT an arrow: `name → state` read as an addressee ("像是给另外一个 working 的人发的", owner same day). The marker is deliberately NOT `[tmm] `, which means "the app is narrating" and folds into a grey sys row — the treatment this note was moved out of.

### What we observe has an input half too

`userPromptSubmit` carries the submitted `prompt` (measured, kiro-cli 2.16.2), which is the only record of text typed at an agent's own keyboard and the only proof that a line `deliver_mentions` typed was accepted as a prompt — `send-keys` succeeding says nothing about that. `telemetry::record_delivery` QUEUES the typed line (`Rec.pending` is a Vec — as ONE slot, a second message typed at a busy agent erased the first's record, so when the agent finally submitted the first queued line nothing matched it: it came back as `via: local` and rendered as an "input" row while its message kept a hollow ring for ever — owner, 2026-08-20), `record_prompt` matches on CONTENT and removes exactly what it found (one submitted prompt can carry several queued lines and acks all of them; `feedBlocks` likewise marks EVERY message an echo contains, not just the newest; **the containment runs whitespace-BLIND on BOTH sides, and on the client it is TRUNCATION-aware** — the stored echo is cut at `MAX_PROMPT_CHARS` (1024) + `…` while the server matched the FULL prompt, so `feedBlocks` (`echoContains`) also accepts a body that starts inside a truncated echo and continues past its end (board #78, 2026-09-03: a 1041-character paste was acked by the hook yet kept a hollow ring for ever because the client demanded the whole body inside 1024 characters);  — `strip_ws`/`squashWs` remove every whitespace character, because a newline in the body never survives the trip: a TUI composer renders it as a space or its own wrap (owner, 2026-08-22), and tmux in extended-keys mode DROPPED the raw `\n` byte outright so the echo came back with the lines GLUED together — squash-to-one-space could not contain that (owner, 2026-08-24, measured in the translator room: `AgenticAI\nAgentic…` echoed as `AgenticAIAgentic…`). The delivery itself is fixed at the source too: `tmux::send_command` routes any text containing `\n` through `paste_text` — bracketed paste is the one channel that carries a newline INTO a composer, where send-keys loses it and a named `Enter` would submit the half-typed line) and emits a `prompt` event with `via: app|local`, `sweep_deliveries` reports what is still pending after 45 s as a `warn` — but **the ack clock does not run while a turn is OPEN**: a busy agent QUEUES what we typed (kiro says "Type to queue") and submits it when the turn ends — and for managed kiro agents that is now pinned in config: `settings/cli.json` carries `chat.defaultInterruptBehavior = "queue"` (owner, 2026-08-20: 默认 Queue 不要 steer — a queued line arrives whole as the next prompt instead of steering the running turn; canonical keys in ONE place `spawn::kiro_cli_settings`, written at spawn, backfilled by `refresh_hooks` on every start, mirrored in `team/backends.rs`) — so `delivery_overdue` skips `running`/`waiting` windows and otherwise measures from the LATER of the typing time and the turn's end (owner, 2026-08-19: "有一些queue的指令，没办法马上confirm，这个不用立刻就unconfirm"). A line typed at an IDLE agent keeps its own clock and a hookless window is still swept — both are tests. Client side, `feedBlocks()` consumes an `app` echo as a *delivered* mark on the message instead of repeating its text, keeps receipts and warnings visible at EVERY detail level (they are about a message the user sent, not opt-in telemetry), and folds a window's `tool` events into ONE lane-per-turn group so `+ tools` can be the default (a tool row keeps 2 KB of its ARGUMENT — it kept 80 chars, so every row ended in `…` after a third of a line with a blank wide screen beside it — and Pre/Post are collapsed to ONE row in `record_tool`, since both hooks are subscribed for backend coverage and an already-spawned agent keeps its old config): only that window's OWN rows end its run (its reply — attributed via the `windowOf` map — its prompt, the invisible echo of a delivered line, a note about it), because folding merely CONSECUTIVE events turned two concurrent agents into one group per call and read as churn (owner, 2026-08-19). A group is OPEN by default with a scrolling body capped at a CONFIGURABLE row count (`hubPrefs.stepsRows`, default `STEPS_ROWS` = 5 — owner, 2026-08-24: "最大显示的行数应该也变成一个可配置的参数…默认…5 行"; a Settings stepper next to the feed-level control, `clampStepsRows` pins 3–30 on both the setter and what localStorage hands back) and a "show all N" that lifts the cap; the ARGUMENT is never truncated — the lane is THREE columns and the MIDDLE one is the only scroller — `.st-scroll` (flex:1; min-width:0; overflow-x:auto) wraps the text in the MARKUP, the name and time are flex siblings BESIDE it, `.s-body` is overflow-x:hidden. Structure beats paint: the sticky-column build failed three ways (columns jumped 30px — sticky offsets measure from the scrollport's padding box; then painted `--surface`, a 3% wash that covers nothing; then still leaked into the lane padding beside the name, since a sticky column covers only its own box — "参数穿模到工具名左侧了"). `min-width: 0` is load-bearing (a flex child refuses to shrink below content without it); rows pan independently by accepted trade; `Hub.source.test.ts` pins the markup shape because an ellipsis hid the one thing you opened the lane to read (owner, 2026-08-20), and `.st-text` must stay `nowrap` and never `pre`: a tool detail contains real newlines, and `pre` would make one call a three-line row and break the cap's single-line math (`hub/Hub.source.test.ts` pins both) — every call is in the DOM, the cap is a viewport on it, so a live run cannot grow the conversation and the inner tail sticks to the newest call until the user scrolls up in it. No emoji in that surface: lifecycle lines carry the machine marker `[tmm] ` and the client renders them (`systemLine()` still accepts the old `⚡`/`✔` bodies — rooms are persisted); consecutive lifecycle lines fold into ONE `sys` capsule, and the chat-only level drops them (the app's record, not the conversation). Inside that capsule each line is its OWN ROW speaking ONE grammar — who, action, detail ("都用统一的 ui 来展示…包括 agent 的名字，状态，或者发送的指令", owner 2026-08-24): `sysParts()` parses every shape into `{who, verb, text, cmd}` (`removed k`, `spawned dev — brief`, `/model x → dev, rev` — the command splits at the LAST ` → `, the one `hub_command` appended), and each atom reuses a dialect the feed already has instead of inventing a third: the name wears the bubble header's ink (`.m-head` 650-weight accent), the action wears the status badge stripped to dot + coloured word (tinted by `sysVerbColor()` in the SAME progressive status language as `noteStateColor`/`stateDotColor` — accent = started moving, green = ended well, grey = at rest, amber = interrupted, red = destructive; both pure + tested, always a token so both themes read it), and a `/command`'s row keeps the typed line as ONE object in the inline-code dialect (mono, soft `--code-bg` wash, accent lean — splitting it into a micro-pill name plus loose args read as fragments, and drawn frames on the inner atoms read as chrome: owner, 2026-08-24 "带参数的渲染好像不是很好" then "不用这种边框的"), with the targets standing as the who. Two rules keep it honest: an unrecognised line shape keeps NO verb or name and renders whole (guessing would truncate the rest), and the per-row ellipsis sits on the text so a long detail cannot eat the badge.

### Hook-sourced auto-replies — four invariants that must live in code

when a managed kiro window's stop hook fires, `consume_file` in `agent_notifications.rs` automatically posts the agent's final reply (`assistant_response`) to the project room. Four invariants prevent this from misfiring; violating any one breaks the system silently so they are enforced in code, not just in prompts: **(1) Same-turn dedup** — `userPromptSubmit` resets the per-turn flags per window; a `tmm send` sets `sent_this_turn` (the agent already spoke INTO THE ROOM this turn); if the flag is set at stop time the auto-post is skipped so one turn never produces two messages. A `tmm done` does NOT set it: the summary is a report ABOUT the work while the stop hook carries the answer itself, and treating done as send made every turn that ends with the REQUIRED `tmm done` lose its final reply — the chat showed a one-line `[tmm done]` and the answer nowhere (owner, 2026-08-21: "kiro grok 都好像没看到最后返回的消息"). Instead `hub_done` records the summary (`mark_done_this_turn`) and `reply_is_the_done_summary` skips the auto-post only when the reply IS the summary verbatim — the one real duplicate. That reset is the ONLY one, so the turn-start hook has to be installed **in every config that can auto-post** — ALL FOUR backend hook sets in `projects/spawn.rs` (`kiro_hooks`/`claude_hooks`/`codex_hooks`/`grok_hooks`; claude and codex shipped without it until 2026-08-22 and their agents lost the auto-post after their first `tmm send` — `refresh_hooks` backfills on every start) as well as the global `kiro_default.json`. Ship `stop` without `userPromptSubmit` and the flag is sticky: the prompt tells the agent to report progress with `tmm send`, and the first such call kills the auto-post for every later turn of that window.

**(2) Record-only** — every hook-sourced post is passed to `hub_post` with `record_only = true`, which prevents `deliver_mentions` from running; if an auto-post body contains an @-address and delivery were allowed, that would type into the peer's pane, trigger the peer's stop hook, which would auto-post back — a ping-pong loop. Skipping the sender's own window does not prevent this: the peer's window is what triggers the loop, so the fix must be at the call site.

**(3) Managed-only gate** — `maybe_auto_post` checks that `<project_path>/.tmm/agents/<window_name>/` exists before posting; the global `kiro_default.json` (used by direct and adopted windows) also carries the stop hook, so without this gate any kiro the user starts by hand would start posting into project rooms.

**(4) Reply budget** — `MAX_REPLY_CHARS = 6144` is the chat-path ceiling (the old 240-char `MAX_SUMMARY_CHARS` retired with the unread-notification UI, 2026-09-01 — the room is the one notification surface). Wiring: `RoomPoster` trait in `agent_notifications.rs`, implemented by `TeamRoomPoster` in `server/mod.rs`, injected once at server startup via `notifications.set_room_poster(...)`. `None` on mobile (degrades silently — no auto-post).

### A done summary reports UP the spawn edge

`tmm spawn` records `spawned_by` in the launch recipe, `build_prompt` NAMES the briefer ("briefed by your teammate lead" — the anonymous "your teammate" left the agent with nobody to report back to), and `hub_done` delivers a non-empty summary into the live managed spawner's pane (`[tmm chat <ts>] <name>: [done] <summary>`, same `record_delivery` bookkeeping as an @mention). Reason: every other completion channel is record-only — the `[tmm done]` room line and the stop-hook auto-post wake nobody — so a lead that spawned two builders never learned they finished and could not schedule (owner, 2026-08-29). This is a TARGETED delivery, never a mention scan: invariant 2 of the hook-sourced posts is untouched, one line reaches one pane once per turn end, and the `spawned_by` chain terminates at the human (empty `by`, also what backfilled pre-recipe agents have), so it cannot loop. The prompt also casts the summary as ONE OR TWO LINES — the full reply is auto-posted separately, so a long summary re-told the whole answer as a near-duplicate bubble.

### Vitals are SNIFFED from the pane, because a CLI's live state has no API

`projects::vitals` reads the last lines of a managed agent's pane and `hub_agents` attaches `vitals` (model, `context_pct`, effort, branch) — every field optional, an unreadable pane yields the empty reading not an error, the object is omitted when nothing is read, and it never replaces the hook-derived state (hooks are facts; this is a reading of somebody else's screen). **The card shows the model WITHOUT its provider prefix** (`modelLabel`: `openai.gpt-5.6-sol` → `gpt-5.6-sol`, `us.xai.grok-4.6` → `grok-4.6`; only known vendor/region words are dropped, so `gpt-5.6` keeps its version dot) — the prefix is the route, not the model, and a 4-across phone row has no room for it (owner, 2026-09-03: "agent卡片显示的前缀可以省略掉"); the registry and the launch line keep the full id, because that is what the CLI needs.

**Each backend is its own dialect** (`sniff_remembered` dispatches on the backend `agents::detect` reported — reading one CLI's screen with another's grammar yields confident nonsense): kiro's own source documents its layout — segments joined by `·` in the fixed order `agent · autonomous · model · effort · context · tangent · codeIntel · goal` (left) + `location · branch` (right), context being "Share of the context used"; grok (1.0.5, measured) paints a header line with the context RATIO at the end (`47K / 500K`, top-right — the percentage is computed, K/M suffix REQUIRED on the total and used≤total, which keeps a `3 / 5` in ordinary output out) and its model in the input box's bottom border (`╰── Grok 4.6 (Bedrock) · always-approve ─╯` — first `·`-segment inside a `╰…╯` line; the approval mode is not a vital); codex (0.148.0, measured 2026-08-22 and 2026-09-03) paints its configurable `tui.status_line` as the footer — the inherited `~/.codex/config.toml` sets `["model", "context-used", "current-dir"]`, i.e. `openai.gpt-5.6-sol · Context 5% used · /tmp/x`, chosen so a 44-column pane (codex TRUNCATES with `…`, never wraps) keeps model and context: `openai.gpt-5.6-sol · Context 5% used · /t…`; items are read BY SHAPE so any order works (`Context NN% used|left` is the context, a `/`/`~` segment the cwd, a 1–2-token digit-bearing slug `<model> [<effort>]`, a `…`-cut word is not an effort), and a line is the footer only with a model segment plus a cwd or context segment; the default footer `<model> [<effort>] · <cwd>` and the older spellings `NN% context left` / `NN% left (… used / …)` still read — LEFT where kiro says USED, so those are `100−NN`; claude uses its official `statusLine` JSON: managed/global settings run local `tmm claude-statusline`, which paints the uniquely anchored `[CC] · <display_name> · N% ctx · used/size · effort <level>` row; `sniff_claude` accepts ONLY `[CC]` as segment 0 (ordinary output is inert), `claude_status_line` strips a trailing `(… context)` off `display_name` (a `[1m]` pin reports itself as `Fable 5.1 (1M context)`, and the parenthetical is a fact about the pin, not the model — owner 2026-09-02), and model+percentage lead so a real 44-column Fable 5.1 pane truncates only counts/effort; four kiro rules follow: the effective Kiro agent identity is the anchor for the positional model field — normally the managed window name, with the exact built-in `kiro_default` accepted for resumed legacy conversations (measured `chat` window retained `kiro_default · gpt-5.6-sol · ◔ 6%`); arbitrary first segments remain inert (else a cwd or a neighbour's line becomes its model); context/branch are found BY SHAPE anywhere in the tail because a narrow pane wraps right-hand segments — while a WIDE pane right-aligns `location · branch` on the SAME line joined by a padding run of spaces, so ≥2 spaces is a segment boundary too (2026-08-26: the glued cwd ate the context percent) — but EFFORT has no shape (a bare `low`…`max` word read anywhere turned table cells into readings), so it is matched by the status line's own pattern — on the anchored line, the segment immediately BEFORE the context segment (`… · model · effort · ◔ N%`) — and its ABSENCE there beside a context segment is a VERDICT (`effort_definitive`): kiro omits the segment when the effort is the backend default, and backfill must not resurrect a remembered one (a once-misread effort was a permanent ghost, re-inserted with a fresh timestamp every poll); a bare `69%` is NEVER the context (only the pie glyph `○◔◑◕●` or a `ctx` suffix counts — a terminal is full of percentages and a confident wrong number is worse than none); the tail is read bottom-up so the newest paint wins. Managed-only, one `capture-pane` per agent, ≤4 per project.

**A miss is NORMAL, so the reading remembers — and events keep the memory warm**: `sniff_remembered` keeps the last good reading per (session, window) and fills gaps FIELD BY FIELD (a pane often shows the wrapped branch line while the status line has scrolled off), a fresh value always wins so a `/model` swap shows at once, the memory expires after 1 h and `retain_windows` drops it with the window. Polling alone left the card empty until a poll happened to catch the status line (owner, 2026-08-25: "经常看到没有信息，过了一会儿才出来"), so `sniff_window_soon` now sniffs AT THE EVENTS that make a pane fresh — every hook edge (turn open, tool, stop/ask) and every delivered chat line — ~1.2 s delayed (the TUI needs a beat to repaint), throttled per window (3 s), on a throwaway thread (telemetry may never block what it observes), same managed-only gate, no-op under `cfg(test)`; `hub_agents` then answers from the memory. Treating each miss as "no information" is what made the card blink (owner, 2026-08-19). The other half was a client bug: `loadAgents`'s `catch { agents = [] }` emptied the whole roster on one timed-out RPC — "I could not ask" is not "there is nobody", so a failed poll now keeps the last roster and only `selectProject` clears it. The reading is PERMANENT on the card (owner, 2026-08-19): model + effort on a second line at `--fs-micro`, and `context_pct` as a 2px line at the card's bottom edge — absolute, so it costs no height. Branch/cwd stay in the tooltip + menu header (project-wide, so per-card they are chrome), as does the exact number — but the menu header quotes NO model: the model's home is the config page, and the menu carries a "configure agent" item that jumps there (App routes it: `openAgentConfig` → `switchTab('agents')` + an `{name, n}` editRequest that AgentsPage fulfils once `defs` load; owner, 2026-08-25: "菜单里不应该有模型名，可以有一个跳转到模型配置的页面的选项"). `ctxColor()` (pure + tested) returns a THEME EXPRESSION — a `color-mix` between the four `--status-*` tokens, never a literal colour, so it is right in both themes — anchored on kiro's own ramp (green ≤20%, amber by its 60% warning threshold) and continuing into hot/danger because >85% is about to force a compact.

### Transient model errors are auto-continued, with the owner's three rules AS the code

(`projects/recovery.rs`, owner 2026-08-22: "自动帮我处理异常…自动帮我发送 continue 指令"): a backend sometimes aborts a turn with a load-shedding error (kiro paints `An unexpected error occurred during the response stream … ModelTemporarilyUnavailable … please try again`) and then sits at its prompt — alive but stalled until a human types. The capture tick (20 s) scans every managed agent's VISIBLE screen and types `continue` at one showing such an error. (1) an INCIDENT is one error INSTANCE, identified by its `error_signature` (the request_ids read off the visible error lines + hit count) and continuously visible — "an error is visible" alone cannot tell a SECOND failure from the first one's still-painted text, so a signature change (the resumed turn died again; owner 2026-08-26: "有可能还会出现二次报错并停止…就需要再次发送指令") replaces the record wholesale — confirmed, mid-backoff or given-up alike — and the new incident sends immediately with a full budget; each incident gets ONE `continue`, verified through the hooks — before any retry the tracker asks `telemetry::turn_fact_since(sent_at)` (accepted prompt / turn end / tool call after the send), because the error text stays PAINTED long after the agent moved on, so the screen cannot say whether the send worked (owner, 2026-08-26: "系统会反复发送好几次 … 通过 hooks 查看之前发送的指令是否正确生效"); a verified send CONFIRMS the incident and it goes silent until the error leaves the screen (the tick that no longer sees it drops the record — a fresh error later starts a fresh budget); (2) UNVERIFIED retries back off exponentially (`BASE_BACKOFF_SECS=30 · 2^(n-1)`: immediate, 30 s, 60 s, 120 s) and after `MAX_ATTEMPTS=4` the window is left alone with ONE `warn` event; (3) an observed TOOL CALL (`telemetry::record_tool` → `recovery::note_tool_activity`) confirms the incident WITHOUT erasing it — erasing re-opened it against the still-painted error and re-sent `continue` into a working agent, the owner's repeat-send report. Detection is deliberately NARROW — a pane is full of text ABOUT errors (the owner pasted the error into chat, which typed it into an agent's pane): a hit needs the error's own header AND a transient marker on the SAME logical line (capture -J joins wraps) — TWO kiro shapes are recognized: the `An unexpected error occurred … ModelTemporarilyUnavailable` stream error, and (2026-08-26) `The model you've selected is temporarily unavailable … '/model' … try again`, whose whole first sentence is the header and self-contains the transient reason — and any line carrying `[tmm chat` is a QUOTE, never a hit. A missed real error costs one manual `continue`; a false positive types into a working agent. `Tracker` is pure (now injected, tested); `check_once` is fail-soft throughout and each `Send`/give-up emits a `warn` activity row so the feed shows what the app did on the agent's behalf.
